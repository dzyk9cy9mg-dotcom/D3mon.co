# D3MON.CO: notes for Claude

**New session? Read [HANDOFF.md](HANDOFF.md) first** for where the last session stopped, then come back here.

The community site for crypto callers, trading bots and chart scripts. We're building the **Arena**: the Battle of the Bots system. [ARCHITECTURE.md](ARCHITECTURE.md) is the blueprint. Read it before changing anything under `server/arena/`.

**Never put secrets in this file or anywhere in the repo:** no API keys, passwords, tokens, server addresses or account emails. Settings come from environment variables or `.env`, which is git-ignored.

## Commands

```sh
npm start        # http://127.0.0.1:3000. The first account to sign up becomes owner
npm test         # node --test; the jsdom page test needs `npm install` first
npm run users    # list accounts and roles
npm run role -- <username> admin|member|owner|ban|unban
npm run kalshi:check   # reads Kalshi's latest rounds and shows how each is scored. Records nothing
```

- Node ≥ 20 and **no runtime dependencies**. Keep it that way, and ask before adding one.
- **Deploy:**
  - The server is AWS Lightsail with the code in `/srv/d3mon`, run by the systemd unit `d3mon`.
  - **The data folder is `/var/lib/private/d3mon`**, set with `D3MON_DATA_DIR`. It's not `/srv/d3mon/data`. Always use this path in server steps.
  - `/var/lib/private` is readable by root only, so commands that look inside it need `sudo`.
  - To update:
    1. Back up: `sudo cp -a /var/lib/private/d3mon /var/lib/private/d3mon.bak-$(date +%F-%H%M)`. The time is in the name because a second backup with an existing name would be copied *inside* the first one.
    2. `cd /srv/d3mon && sudo git pull && sudo systemctl restart d3mon`
  - **d3mon.co is still behind the Under Construction page** (Caddy, `/etc/caddy/Caddyfile`). Browsers that opened the owner's private preview link get a cookie and reach the app. On 2026-10-17 a `@botapi` block was added so `/api/v1/bot/*` and `/api/v1/stat-catalog` reach the app without the cookie, letting bots connect with their key while the public still sees the construction page. The backup is `Caddyfile.bak-2026-10-17-0104`. Never write the preview link or cookie value into the repo.
  - **Settings and secrets on the server:** the `d3mon` unit sets `D3MON_DOTENV=off`, so the app never reads `/srv/d3mon/.env` itself. The file (mode 600, root) is loaded by systemd through the drop-in `/etc/systemd/system/d3mon.service.d/discord.conf` (`EnvironmentFile=/srv/d3mon/.env`), added 2026-10-19 for the Discord link. After editing it: `sudo systemctl restart d3mon`. To check it without showing secrets: `sudo grep -o '^[A-Z0-9_]*=' /srv/d3mon/.env`. **The Discord link is live** (2026-10-19): 22 channels linked, main channel `#stream` (the first channel in `D3MON_DISCORD_IDS`)
  - The role and user commands must be given the data folder, or they'd read `/srv/d3mon/data` instead: `cd /srv/d3mon && sudo D3MON_DATA_DIR=/var/lib/private/d3mon npm run users` (and the same for `npm run role -- <username> admin`).

## How the owner wants work done

- **One step at a time.** Test each component before moving on. Never claim something works without running it.
- **Keep messages to the owner short and simple:** one topic per message, no long lists, plain words. End every message with one clear **"Your next step:"** line.
- **Deliver work as pull requests** for the owner to review and merge. Then walk them through the server update step by step.
- **API first.** Every feature is a `/api/v1` JSON endpoint plus live feed events. Pages are thin clients, because the front end will be rebuilt as an immersive 3D site. Don't put logic in `public/js/d3mon.js`.
- **Branding (owner, 2026-10-19): it's always D3MON, never "Demon"**, anywhere on the site, in docs and in messages (the D3MON Discord, not the Demon Discord). Where it's clever, a 3 can stand in for an E to market the idea of the three (callers, bots, chart scripts), e.g. the 3 in D3MON itself; don't overdo it, and never in a way that hurts reading.
- **Always "Kain and Abel", in that order** (owner, 2026-10-23): in every name, menu, heading, column and list, Kain comes first.
- Bot owners share **read-only stats only**. Refuse anything that looks like a key or secret (`server/arena/validate.js`).

## Decisions made

| Decision | Why |
| --- | --- |
| Arena data is in `arena_*` collections of the existing store. `rules.js` makes them server-only: `/api/db` can't read or write them, admins included | `/api/db` is public-read by default. Privacy and validation must be enforced on the server |
| Strict allowlist schemas: unknown fields get a 400. Field names and values are scanned for credentials (PEM, `sk-`, JWT, UUID key ids, long hex or random tokens, BIP-39 seed phrases) | "Never take trading credentials" |
| Applications are never deleted. Every status change goes into `history`. Statuses are pending, approved, rejected, withdrawn, and a reopen goes back to pending | Owner wants a full application log |
| **Joining D3MON needs no battle** (owner dropped the hosted show, 2026-10-17): `POST /api/v1/applications` is an application with `battleId: null`, new entrants only (no `entrantId`), reviewed by an admin like any other. Approval saves the entrant with `battles: []`. A name already saved is `already_joined` (yours) or `name_taken` (someone else's) | Bots need a way in for the tournaments; an admin still approves each one to keep out spam |
| Each battle needs its own application. Approval saves an **entrant** (stable id and slug) that its owner re-selects later with `entrantId` | Owner's rule. Bots get identities instead of name-matching |
| Entrant slugs use the page's own `slug()` rules (30 characters) | So they line up with `config/battleRoster` names the current page uses |
| Public entrant fields: name, kind, creator, Discord server. The alternative account and notes are visible only to the owner and admins | Privacy by default |
| HardSmoke means any `admin` or `owner` role (`isAdmin`) | No separate host role is needed yet |
| **A battle shows as "over" once its last round ends** (`battleState`, `state` and `over` in battle views). Its stored `status` is never changed; drafts and final battles keep theirs. `/apply` offers only battles still to come, the server refuses applications to (and withdrawals from) a battle that's over, and "current" display slots skip live battles that are over | Old battles stayed "open" forever and were offered on `/apply` (owner, 2026-10-17). Status stays HardSmoke's choice |
| Battles start on a quarter hour and default to 8 rounds of 15 minutes on `KXBTC15M` | They follow Kalshi's BTC 15-minute rounds |
| The live feed (`/api/v1/feed?topics=`) builds each event per reader and re-checks roles on every event. Signing out ends the stream | Privacy is enforced on the server, never just hidden in the page |
| Calls are made **during the round** and close a few minutes in: `callWindowMin` per battle (0–15; **15 by default = any time until the round ends**, owner 2026-10-17; 0 = before the round starts), decided by the **server clock**. Revised 2026-10-17 from "locked at round start" | Tester crazylion found bots call during the 15-minute round, like Kalshi traders, so nothing they sent counted. The server clock still decides, as browser timestamps can be backdated |
| **One call per entrant per round, final when made.** A retry is `unchanged`, a different call is `already_called`, and a call is never moved to another round on its own. Without `round`, a call goes to the round open now | Owner: bots usually make one call per round. The old silent move to the next round confused the tester |
| The ledger arrived in step 3, not 4, as the home for metric and score lines. Each append is fsync'd before the request is answered | Round results must survive a crash. The 1 s store delay doesn't guarantee that |
| Manual metric `speedMs` is lead time before the lock (more means earlier) | One meaning for manual and automatic speed |
| Profit is recorded in any or all of three units, each optional and signed: `profitUsd` (cents), `profitPerContract` (per $1 Kalshi contract, −1 to 1, 4 places) and `profitPct` (percent return, −100 or more). Totals: dollars and per-contract add up, percent is averaged per round | Owner confirmed dollars and asked for the option to use all three |
| A metric entry's `correct` must agree with its `call` and the round result. A later result correction flags `mismatch` and doesn't rewrite entries | Mistakes stay visible. History is never rewritten |
| A Kalshi result beats a hand-entered one, and once there is one, a different result can't be entered by hand | Verified data wins |
| **Every call is sealed until its calls close** (owner, 2026-10-23, reversing 2026-10-17's "bots shown live": people pay to subscribe to these bots, so their calls mustn't be copied for free). Outside battles calls close at the round's end. Everyone sees that a call came in and when; its owner and admins see the direction. During the round `GET /rounds/:round/calls` gives `crowd { called, up, down }` for bots and scripts, with `up`/`down` null until `CROWD_MIN` (3) have called. **Exceptions:** a bot's or script's call made in a **Battle of the Bots** round (`battleIds` not empty) is shown live; the **Capstone** room shows its featured entrants' calls (callers and bots) the moment they come in; **Kain and Abel** call live (below). **Only callers give a "why"**: one sent with a bot's call is dropped. Verified stats count a call only after its close | Nobody can copy a paid bot's call for free, and the floor still shows the crowd. Changing it is one condition in `Calls.view` |
| Only an entrant's owner can make its keys (admins can revoke). At most 3 active keys per bot or script. Callers get none. Tokens are `d3b_<keyId>_<secret>`, shown once, and only `sha256(secret)` is stored | Whoever makes a key sees it, and rotating needs a spare |
| A call records the battles its entrant was in for that round (`battleIds`), and a board shows only those calls | Calls belong to the battle record even if the lineup changes later |
| Card readers: guests see public stats, members public and members-only, the owner also private. **Admins read like members**, so private means private. Admins can still see raw calls on the board and history | The owner's privacy choice holds for everyone |
| Verification is per stat: "verified" (all results from Kalshi), "recorded by host" (all by hand), "mixed" (with `sources` counts). Call counts and lead time are "verified" because they're server-stamped | Honest labelling while results are still entered by hand (before step 5) |
| A call is stamped with the same clock that checked its lock (`ledger.append(…, at)`) | One clock decides both, and tests can move it |
| Custom stats: up to 20 per bot, the type locked once values exist, and removing one keeps its history (defining the key again restores it). Values must match the declared type, and unchanged values are skipped | Self-reported data stays consistent and its history is never lost |
| The bot stats rate limit counts only pushes that write. Bad requests fall under the key's general limit | A developer fixing their requests isn't locked out |
| The main page's roster is fed by **one battle at a time**, chosen by HardSmoke (`onMainPage`), never automatically, and never a draft. Stream links are kept, and every write records the previous roster in the ledger | It overwrites what HardSmoke may have typed on the old page, so it must be deliberate and recoverable |
| Kalshi round = the market's `open_time`. `result` yes = up, no = down. Only `finalized`/`settled` markets with `strike_type` `greater_or_equal` are read | Checked against what Kalshi returned to the server on 2026-10-15. Anything else is skipped, not guessed |
| Kalshi writes its own score line even when HardSmoke already entered the same result | Kalshi's line is what makes the round "verified" |
| Kalshi is polled 8 s after each close, every 20 s early in a round, every 60 s otherwise, and backs off on errors. Rounds with calls or in a battle that are still unsettled 30 minutes after they end are flagged for HardSmoke | Settlement comes about 4 s after close. The manual fallback stays |
| No leaderboard. Stat cards are per entrant. Every stat starts hidden | Owner's spec |
| **Stats Hub:** cards carry **verified** stats (server-computed from the entrant's own calls, keys `v_…`, every entrant) and **self-reported** ones (the stat list and custom stats, bots and scripts only). Battles keep server/Kalshi scoring | Owner's spec, then the owner agreed verified caller stats, and bots showing claims next to results. Privacy (hidden by default) wins everywhere |
| Callers make their own calls on `/my` (Up/Down, server-locked) and their card is verified stats only | Owner never enters callers' calls by hand |
| Script and bot owners can type self-reported values on `/my` (`POST /api/v1/entrants/:id/stats`, ledger `via: "owner"`) as well as send them with the key | Chart scripts often can't send a keyed request. Owner agreed |
| Main page (`d3mon.js`) gets no new battle features: the 3D site will read `/api/v1`. Its community Up/Down buttons stay (they're a members' game, not battle calls). The battle header just links to `/my` ("Make your battle call") and `/board`. **Temporary:** it goes when the 3D site replaces the page, so don't build on it | Work on the old page would be thrown away. Owner agreed |
| The standard stat list lives in `arena_statcatalog`, edited by HardSmoke on `/catalog`. The seed only adds missing stats. Stats are retired, never deleted, and a type locks once values exist | Editable without code changes; history stays readable |
| Old settings for the removed computed stats (`arena_statsettings.stats`) are kept but never read. New settings are under `catalog` | A choice made for a verified stat must not publish a self-reported one |
| A list key an owner already uses as a custom stat stays theirs for that bot | Their history and type come first |
| **The stats monitor shows a value only when its owner made it Public or Members only.** Hidden and private stats show activity (updated when, how often, how, errors), never the value | Owner: "I do want owners to have the power to keep private." The same rule as cards, where admins read like members |
| Refused pushes are logged by error code, field and key name only, never the content | A refused value may have been a secret |
| **Display slots:** pages name a slot (`data-d3mon-display="key"`) and HardSmoke decides its bots, stats, layout and order on `/displays`. Values come from `Stats.card()` per reader. Bot order is "as listed" or "by name", **never by a stat's value** | API-first for the 3D site; owner privacy everywhere; "no leaderboard" |
| **Tournaments: "Join tournaments" is the owner's switch** (`PUT /api/v1/entrants/:id/tournaments`), bots and scripts only for now, off by default. It counts from the **next** round, leaving keeps rounds already played, and each switch is a `tournament_entry` ledger line; the latest one whose `from` has come decides. Anyone can see whether a bot has joined; the history is for its owner and admins. Admins can't join a bot for its owner | Opt-in per bot (owner). Joining mid-round would let a bot join after seeing the price move |
| **Tournament standings** are worked out from the ledger on each request, nothing stored: hourly, daily (from midnight), weekly (from Monday) and monthly (from the 1st), all in **US Eastern** (`America/New_York`). An entrant scores only in rounds it was in and only once **Kalshi** settled them (hand-entered results don't count; a round Kalshi never settles counts for nobody). Rank: most correct calls (a missed round scores nothing), then accuracy, then the earlier average call (lead to the calls close); exact ties share a rank. Active bots and scripts only. Public, with the "not financial advice" notice in every response | Owner agreed the four points; verified data only, so a host can't sway a ranking |
| **Tournament results are saved once and never rewritten**: a `tournament_final` ledger line when every round is settled by Kalshi, or 30 minutes after the end. Before that the status is `scoring`. A later Kalshi correction sets `corrected: true` and leaves the saved standings alone. The saver only runs when Kalshi polling is on (`cfg.kalshi !== false`), so test servers never save on their own; tests call `finalizeDue(now)` | "Final results never rewritten; a correction is flagged" (plan). Same rule as battle metrics |
| **Tournament admin controls:** removing a bot counts from the round **in progress** (earlier rounds stay, saved finals untouched), the reason is for its owner and admins, and the owner can't rejoin until an admin restores it (from the next round). A pause also covers the round in progress, resumes from the next round, and its reason is public. Paused rounds are never counted as settled, so they count for nobody | An admin acting on cheating or a Kalshi outage shouldn't wait a round; history is never rewritten |
| **The VIP Room** (`/vip`, `server/arena/vip.js`, owner 2026-10-18) is the paid room at the pyramid's peak. An admin grants access by username for 1–366 days (`POST /api/v1/vip/access`); more days extend from when access runs out; it ends by itself, or an admin ends it early. Admins always have access. Admins choose up to 20 featured entrants (`PUT /api/v1/vip/featured`, public list). In `GET /api/v1/vip/room` members see the **featured callers' calls before the close**; every other endpoint keeps them sealed. Ledger lines `vip_access`, `vip_featured`. Payment is outside the site for now; Stripe later. Caveat: a VIP member could see a featured caller's call early during a battle that caller is in | The owner wants paid access without a payment system yet; it's the room's value |
| **Every call is priced at Kalshi's own price for the side called** (`server/arena/prices.js`, owner 2026-10-18): the server reads the open round's prices the moment a call arrives (`call_price` ledger line, source `live`, with `lagMs`); if Kalshi can't be reached, the last price read for that round up to a minute old (`snapshot`); for older calls, Kalshi's one-minute candles, the last minute that ended before the call (`candle`), backfilled every 5 minutes once Kalshi has settled the round. Up pays YES's ask, Down pays NO's ask; **paper profit per $1 contract** is 1 − price when right, −price when wrong. Shown on the board (`@62¢`, `+38¢`), the trading floor, tournament standings (beside the ranking, never part of it) and three verified stats (`v_paper`, `v_avg_paid`, `v_edge`, hidden by default like every stat). A sealed caller's price is hidden until the close. Prices read as Kalshi's `*_dollars` strings, cents as a fallback; `npm run kalshi:check` prints the raw fields | The owner wants stats worked out on our side from when each call was made and at what price, with nothing a bot can fake. D3MON never trades: paper only, "not financial advice" |
| **The Grand Hall's video** (`server/arena/hall.js`, owner 2026-10-19): an admin pastes a YouTube link (video, Short or live) on `/displays` (`PUT /api/v1/hall/video`, `DELETE` takes it down, `GET` is public); only the provider, the 11-character video id, its kind and a title are kept (`hall_video` ledger line), never the link's tracking. The hall's live event screen shows it and a click plays it in a panel over the world (`youtube-nocookie.com` embed; a Short plays tall); the 2D hall has a Watch button; feed topic `hall`. **The thumbnail** is fetched by the server from YouTube (`i.ytimg.com`, `D3MON_YT_THUMB_URL` for tests) and served from D3MON at `GET /api/v1/hall/video/thumb` (one image kept in memory, only real images passed on, a failure retried after 5 minutes), so the 3D screen can draw it and visitors don't call YouTube until they press play. While the video panel is open the 3D world stops drawing (`scene3d.hold(true)`) and the panel has no backdrop blur (owner, 2026-10-19: the Short paused by itself and wouldn't carry on). **Still open:** that didn't fix it, and the owner moved on; the next check is whether the same Short pauses outside D3MON in `youtube-nocookie.com/embed/<id>` and `youtube.com/embed/<id>`. "Open on YouTube" under the video is the fallback. YouTube only for now, Twitch and Kick later the same way | YouTube won't play on the 3D glass (a cross-origin video can't be a WebGL texture), so the panel is the standard way. Share links carry tracking |
| **The Grand Hall's chat** (`server/arena/hallchat.js`, owner 2026-10-19) is the **main floor of the site's own Cortex chat**, through `/api/v1`: `GET /api/v1/hall/chat` (public, the latest messages, oldest first) and `POST /api/v1/hall/chat { text }` (members). It reads and writes the same `lounge/<hour>` log as the main page (`tab: "main"`), so messages show in both. The server enforces the chat rules the main page only applied in the browser: signed-in members, no bans, no mutes (`config/mod.muted`), the admins' slow mode (`config/mod.slow`, at least 2 s; admins exempt), masked words (`config/mod.words`), 400 characters, secrets refused. Feed event `hall.chat` on any change to the log. The hall's D3MON chat screen shows the latest six; clicking it (or 💬 Chat in 2D) opens the chat panel down the right side | API-first for the 3D site, and the trading room needs people talking now |
| **The site's chat and the D3MON Discord are one conversation** (`server/arena/discord.js`, owner 2026-10-19; setup in [`docs/DISCORD.md`](docs/DISCORD.md)). Links: **`D3MON_DISCORD_IDS`** is one list of ids in any order (owner, 2026-10-19: they're easy to mix up), and Discord says which is a category and which a channel; the **main channel** (`D3MON_DISCORD_CHANNEL_ID`, or else the first channel in the list) is the hall's chat and the Cortex main floor; **whole categories** (also `D3MON_DISCORD_CATEGORY_IDS`; owner: "I don't want to do one channel at a time") add every text channel and voice channel's text chat in them (at most 25), each its own channel: a Discord name matching a built-in Cortex channel (btc, eth, sol, xrp, kalshi, polymarket, off-topic) joins it, any other becomes a Cortex channel `chx["dc<id>"]` in `config/cortex` (so the main page shows it with no change to `d3mon.js`), and the hall's chat panel shows them as tabs (`GET/POST /hall/chat?channel=`). Admins see per-channel `link` health in `GET /hall/chat`, never the secrets. **Only public categories:** the site chat is public | One conversation instead of half-empty rooms. Polling keeps "no runtime dependencies" |
| A coin transfer's `xfer[id].done` and `ok` in `bots/<uid>` are admin-only, and once either is set the entry is frozen for its member: it can't be edited or removed, and the document can't be deleted.
